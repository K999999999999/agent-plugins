# 需求发现

本 Skill 用于 `需求发现`：用户知道现状不理想、发现了机会或想改善某件事，但尚未形成明确候选目标。先帮助用户理解问题，再共同判断是否值得解决以及可能追求什么结果。

如果用户已经提出了候选目标，只是其行为、范围、关键边界或验收仍有重要歧义，应使用 `workflow-grill-with-docs` 进行 `需求澄清`。如果结果和范围已清楚，只缺少可确认的行为 Contract，则进入 `workflow-to-spec`。不要为了走流程重复探索已经确定的目标。

## 探索方式

1. **检查上下文。** 阅读目标仓库适用的 Agent instructions、相关项目事实源、已有工作记录和必要的代码 / 测试证据。只查与当前问题有关的内容；说明事实的来源，并区分事实、用户判断、假设和未知项。
2. **理解问题。** 弄清用户观察到了什么、影响谁 / 什么、在什么场景出现、带来什么成本或风险。证据不足时说明仍未知，不把猜测包装成根因。
3. **形成候选结果。** 与用户讨论可能值得实现的结果、评估选项及其主要取舍。一次只问一个最能区分选项或减少不确定性的问题；可以提供建议，但把建议和用户决定明确分开。
4. **判断是否有目标。** 用户可以选择某个候选方向、修改它、继续探索或暂不行动。不要强迫用户从有限选项中选择，也不要为了结束而假设已达成共识。

## 输出与阶段边界

探索过程中，简要维护：

- **问题与场景：** 已观察的问题、受影响者和触发场景；
- **事实与证据：** 仓库 / 用户提供的证据及其来源；
- **候选结果与取舍：** 可选方向、预期收益、成本和未知；
- **用户决定：** 已认可、拒绝或暂缓的内容；
- **下一步：** 继续发现、转需求澄清、形成 Spec，或停止 / 暂缓。

阶段转换规则：

- 没有候选目标，或用户仍在理解“到底要不要解决、想得到什么结果”：继续 `需求发现`。
- 候选目标已出现，但目标行为、范围、边界或验收中存在会改变结果的重要歧义：转入 `workflow-grill-with-docs`。若原任务只要求探索，则先报告并等用户决定是否继续；若用户目标已包含完成该工程改动，主 Agent 可在本轮继续调用下一阶段，不要求用户手动重启 Skill。
- 目标、预期结果和范围已经足以写出 Contract：转入 `workflow-to-spec`。Spec 是否短版或完整版本以及保存位置遵循目标仓库规则。调用下一阶段不代表需求已确认，也不扩展实施授权。
- 用户决定暂不实施：记录探索结论即可，不创建实施 Spec、Ticket 或代码变更。

本 Skill 不替用户决定候选目标，不创建实现 Ticket、不实现代码，也不把探索结果宣称为已确认需求。主 Agent 可依据阶段结果自动调用后续阶段 Skill，但只有原任务意图覆盖继续实施、且所有 Spec / Ticket / 技术决定门禁满足时才能进入实现；纯探索请求在汇报候选后停止。需要保存阶段状态时遵循目标仓库的工作记录规则；纯探索不强制创建正式 Spec。

## 完成 / 暂停时的总结

```text
阶段: 需求发现
问题与场景: <目前理解的现状与影响>
事实与证据: <来源及已知边界>
候选结果: <选项及主要取舍；尚无候选时说明>
用户决定: <认可、拒绝或暂缓；没有则写尚未决定>
未解问题: <继续探索所需的问题；没有则写 None>
下一步: <继续需求发现 | workflow-grill-with-docs | workflow-to-spec | 等用户决定是否继续；说明是否可在当前任务授权内继续>
```

默认使用中文。Skill 名称、命令名、API、类名、函数名、文件路径和必要的原始术语保持原样。
