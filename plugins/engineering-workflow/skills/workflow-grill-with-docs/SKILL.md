# 需求澄清

只处理 `需求澄清`：用户已经有候选目标，但影响结果的重要行为、范围、边界或验收仍不明确。不负责用户尚不知道想追求什么结果的 `需求发现`（使用 `workflow-discovery`）。不实现代码、不创建正式 Ticket、不提交 Commit、不创建 PR。直接依据目标仓库的 Agent instructions 和项目事实开始；无需先运行 `ask-matt`。沿已有导航按需查找相关领域事实、Contract、代码、测试和运行入口；不要为了完成清单而通读无关目录。

## 先建立事实底稿

先形成简短底稿，并给重要项目事实标出来源。明确区分：仓库事实、用户已确认的决定、尚未确认的假设、建议和未知项。用户描述与事实源或当前行为冲突时，先核实冲突证据，再向用户说明差异；不能默默用旧实现覆盖已确认 Contract，也不能把推测当成事实。

## 覆盖检查

对每个需求逐项判断下列维度是“已明确”“需要澄清”还是“与本需求无关”。这是防止漏问的覆盖检查，不是要求每个需求都增加所有类型的行为：

- 目标、目标用户 / 调用者，以及触发需求的核心场景；
- 当前行为与期望变化，包含可观察的成功结果；
- 与结果有关的领域术语、业务规则和权威事实源；
- 适用时的状态变化、边界输入、失败行为、恢复方式和副作用；
- In Scope、Out of Scope、依赖和兼容性要求；
- 适用时的模块 / 架构边界、权限、安全、数据范围和其他不变量；
- 可观察的验收条件，以及能提供证据的测试、Evaluation、业务验收或运行入口。

只有当某个维度确实不会改变需求结果时，才能标为无关；对会影响实现正确性的关键维度不得静默跳过。至少为核心行为检查一个正常结果，并根据需求风险检查相关边界或失败结果。

## 逐轮澄清

- 每轮只向用户提出一个当前最关键的问题；优先使用仓库证据回答已知项，避免把可查事实变成用户问题。
- 顺序按当前风险调整。通常先解决目标 / 场景和业务含义，再处理范围、关键边界、Contract 与验收；不要为了固定顺序询问无关问题。
- 用户回答后重新检查“覆盖检查”中的所有相关维度，找出新暴露或仍未解决的问题；不能因为已回答上一问就自动结束。
- 如果答案将改变目标、可观察行为、范围、权威事实源、架构 / 安全 / 状态边界或验收，必须继续澄清。若用户明确要求暂缓该决定，记录为阻塞项，不得宣称澄清已完成。
- 只有不改变已确认 Contract 的局部实现选择（例如符合约束的内部组织方式）才可留给 Ticket / 实施阶段，并须标明由实现阶段决定。
- 不为了形式提前创建 ADR、Spec、Ticket 或外部 Issue；本 Skill 不自动调用下一个 Skill。

## 完成条件

只有同时满足以下条件，才可判定需求澄清完成：

- 与需求相关的覆盖维度均已明确，或有证据说明与本需求无关；
- 不存在会改变目标、可观察行为、范围、关键事实源、架构 / 安全 / 状态约束或验收方式的未决问题；
- 重要假设已由用户确认，或已证明不会改变已确认 Contract；
- 成功结果和需要验证的边界 / 失败行为足以形成可验收条件。

“没有任何疑问”指没有会影响正确实现或验收的未决问题；它不要求预先决定 Contract 内的每个代码文件、类名或实现步骤。任何关键未知都应继续提问，或如实标为阻塞，不能用假设填空后宣布完成。

完成或阻塞时输出：

```text
状态: 澄清完成 | 阻塞
事实源与已确认事实: <关键事实及来源>
用户已确认的决定: <目标、行为和其他决定>
范围与关键边界: <In Scope / Out of Scope / 约束>
验收与验证方向: <可观察结果和证据入口>
假设: <已确认或不会改变 Contract 的假设；没有则写 None>
未决 / 阻塞项: <会改变结果的问题；澄清完成时写 None>
留给 Ticket / 实施阶段的决定: <不改变 Contract 的局部选择；没有则写 None>
建议下一步: <根据目标仓库规则推荐一个阶段；等待用户决定，不自动调用>
```
