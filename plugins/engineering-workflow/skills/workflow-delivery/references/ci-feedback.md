# CI Feedback（持续集成反馈与失败处理）

这份 reference 在 Delivery 需要判断 Presubmit / Post-submit、测试稳定性、CI 门禁、自动合并或运行时发布时读取。它不规定固定时间、测试比例或具体 CI 平台。

## 1. Feedback loop

CI 的价值是让问题尽早、清楚、可行动地暴露。对每个阻塞检查，确认：

- 谁能查看结果和日志；
- 失败从什么时候开始、涉及哪个 Commit / 环境；
- 是否能区分代码回归、测试缺陷、环境故障和 Flaky Test；
- 失败后下一步是修复、重跑、回滚、隔离还是补充验证；
- 结果是否足够清楚，不需要维护者重新猜测 CI 的行为。

## 2. Presubmit 与 Post-submit

Presubmit 应优先运行快速、可靠、可复现、与变更直接相关的检查。它可以牺牲部分覆盖范围换取反馈速度，但被省略的风险必须由 Post-submit、Scheduled、Integration、Runtime 或业务验收承担。

Post-submit 可以承载慢速、高 Fidelity、资源密集或较低确定性的检查，但必须有失败通知、Owner、修复路径和适用的回滚 / 停止发布策略。

不要把“所有检查都塞进 PR”当作质量；如果快速反馈被低信号检查淹没，团队会开始忽略整个门禁。

## 3. Flaky Test policy

测试失败后先判断：

1. 是否能在相同 Commit 和环境稳定重现？
2. 是否有生产行为变化的证据？
3. 是否是测试、环境、时间、随机性、共享资源或网络造成的非确定性？
4. 是否有 Owner 和预计修复 / 回收时间？

暂时隔离不是删除证据。隔离记录至少包含原因、影响、替代验证、Owner 和回收条件；到期后要复查。反复重跑直到通过不是修复。

## 4. Rollback 与 Known-good

测试提供“可以改变”的信心，Rollback 提供“可以撤回”的信心。出现高置信度回归时，优先按目标仓库规则恢复 Known-good 状态，再调查根因；不要让一个已知损坏的构建持续阻塞团队。

Rollback 本身也需要权限、数据兼容性和状态恢复判断。不可逆迁移、数据库 Schema、外部 Contract 和运行时配置变化，必须在 Ticket / Delivery 阶段提前说明恢复限制。
