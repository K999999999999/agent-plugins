# Spec 与工作项约定发现

这是 `setup-engineering-workflow` 初始化时使用的只读检查清单，不指定某个固定 Tracker、目录、文件模板或状态字段。

## 探索顺序

- 先读取 Agent instructions、README、贡献指南和工程文档；
- 检查仓库中已有的 Spec、Ticket、Issue、计划、决策和验收记录；
- 确认它们存储于本地文件、外部 Tracker，还是两者都有；
- 查看现有记录的路径、格式、状态、依赖关系、Owner、评审和归档方式；
- 判断当前规则是否能支持从需求到实现、验证与交付的追踪；
- 发现冲突时列出证据和影响，等待用户决定优先级。

如果项目需要跨多个 worktree / session 恢复短期执行进度，额外检查是否已有本机实时状态记录及其稳定工作项 ID、目标仓库 / branch / worktree / PR 引用、最近阶段、验证结果、授权来源和下一步。它与长期 Spec / Ticket 的职责不同，也不应复制整份 Contract。只有目标仓库规则已有约定或用户确认采用时，才提出放入 Git common directory 等本机位置；按目标项目定义原子更新、并发写入、防止损坏丢失和过期记录保留方式。不得假定某个项目的 `.git/harness/...` 等路径适用于其他仓库，也不得从旧对话或记录缺项推断授权。

## 恢复与跨仓库记录

- 用稳定工作项 ID 关联记录，不把 branch 名称或临时 worktree 路径当作工作项身份；清理单个 worktree 时保留仍需恢复的状态和长期记录。
- 跨仓库工作明确唯一主记录及每个仓库的关联记录。关联记录引用主记录和本仓库事实，不复制实施 / 发布授权；主记录不可用时，不从关联记录推断新的远端写入许可。
- 规划如何在本机状态丢失或换机器时，从长期记录、版本库和可核实的远端事实恢复。无法核实的阶段、归属或授权标为未知，不能靠推测补全。

## 提出配置建议

- 足够的项目约定无需重建；
- 缺少必要约定时，根据项目实际工作方式提出最小选择，而不是直接采用固定目录或状态集合；
- 分清工作项跟踪与需求澄清、工作流路由、实现授权和发布授权；
- 分清长期项目记录与本机实时进度记录；确认授权须指向用户决定的来源，不以 PR 正文、branch 名称或历史摘要替代；
- 外部 Tracker、PR 或远程同步不属于默认初始化范围；
- 写入任何新约定前，说明文件路径和内容，并等待用户确认。
