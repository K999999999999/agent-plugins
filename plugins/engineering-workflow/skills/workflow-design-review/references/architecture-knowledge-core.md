# Architecture Knowledge Core

这份 reference 是 `workflow-design-review` 的完整架构判断依据。它用于在设计涉及边界、依赖、公共 Contract、跨边界数据、技术替换、复杂度或重大未来变化时，支持主 Skill 的决策顺序。

它不是模式目录，也不是要求每个项目采用同一种目录结构。审查必须先结合目标项目的 Architecture、Domain、Spec、代码和运行时事实，再使用下面的原则。

## 1. 最高目标：降低整个生命周期的成本

架构设计的目标不是层越多、接口越多、模式越多、微服务越多，也不是为所有未来可能性提前设计。目标是让系统在整个生命周期中尽可能降低：

- 理解成本；
- 修改成本；
- 测试成本；
- 部署成本；
- 维护成本。

好的设计应保护真正重要的业务策略，隔离容易变化的实现细节，让常见变化局部化，让影响范围可预测，降低认知负担，保留合理的未来选择，并使用最少必要复杂度。

“现在能跑”不是充分标准；“看起来很 Clean”也不是充分标准。最终判断是：重要业务是否更受保护，细节是否更容易替换，变化是否更局部，系统是否更容易理解，影响是否更容易预测，同时没有引入超过收益的不必要复杂度。

## 2. 复杂度优先：先寻找三个信号

Design Review 首先检查：

### 2.1 Change Amplification（变更放大）

一个简单需求是否需要修改许多不相关位置？相同业务规则是否散落在多个 Module、Adapter、配置或测试中？

### 2.2 Cognitive Load（认知负荷）

修改一个模块是否必须理解大量其他模块、Framework、基础设施或隐藏约束？一个简单行为是否必须穿越很多层才能看懂？

### 2.3 Unknown Unknowns（未知的未知）

修改某处时，是否难以预测还会影响哪里？开发者是否甚至不知道还要检查哪些组件、状态、配置或测试？这是最危险的信号，应优先处理。

复杂度常来自不必要依赖、隐藏依赖、信息泄露、模糊边界、模糊职责、不一致和不明显的重要设计信息，而不只来自代码行数。

## 3. Business / Use Case / Change Axes

### 3.1 围绕 Use Case，而不是围绕技术栈

项目结构首先应让人看出系统做什么，而不是首先看出它用了什么 Framework。业务规则和 Use Case 是系统存在的原因，Database、Web、Framework、通信和部署机制是支持它们的工具。

审查时问：当前设计是否首先表达 Business Policy（业务策略）和 Use Case？如果技术选择变化，核心业务是否必须随之修改？

### 3.2 按变化原因划分边界

边界的主要依据不是目录、技术栈或执行顺序，而是：

- 什么东西因相同原因一起变化？倾向放在一起；
- 什么东西因不同原因独立变化？倾向隔离。

重点检查 UI、Database、外部服务、供应商、部署机制和业务规则是否被错误地放进同一个变化单元。

### 3.3 避免 Temporal Decomposition（时间顺序分解）

不要因为程序依次执行“读取 → 处理 → 保存 → 输出”，就机械创建四个模块。如果四个模块都需要知道同一份业务知识，这种拆分通常只是把共同复杂度分散了。

模块应更多围绕隐藏的知识、职责、变化原因和真实抽象，而不是只围绕执行时间顺序。

### 3.4 架构不等于部署拓扑

Monolith、Microservices、SOA、Event Driven、Serverless、Plugin Architecture 本身都不代表好架构。服务只是另一种组件交互方式。真正的架构在于边界在哪里、哪些知识被隔离、依赖方向怎样、哪些变化被保护。

不要把技术拓扑误认为软件架构，也不要为了“现代化”或“企业级”自动增加服务和通信边界。

## 4. 依赖方向：策略稳定、细节可替换

总体依赖方向应是：

```text
细节 → 机制 → 策略
外层 → 内层
实现 → 契约 / 业务策略
```

高层策略不应依赖低层实现细节。Business Core 不应被 Database、Web、Framework、LLM SDK、Vector DB SDK、HTTP Client、消息系统、文件系统或部署机制主导。

如果控制流必须从内向外，只有在真实架构边界需要保护时，才通过稳定 Contract、Port 或 DIP（Dependency Inversion Principle，依赖倒置原则）反转源码依赖。不要仅为了“依赖倒置”给每个外部调用机械创建 Interface。

### 4.1 稳定性与循环依赖

依赖应总体朝向更稳定、更核心、更高价值的部分。高价值稳定 Module 不应强制依赖频繁变化的外部或实现细节。

组件依赖图应尽量无环。循环依赖通常表示模块无法真正独立、边界已破坏、修改和发布相互牵制、影响范围不可预测。出现循环时，先重新检查职责和边界，不要只用技术手段隐藏循环。

### 4.2 策略与细节分离

以下通常是可替换细节：数据存储、UI / Web、Framework、外部 SDK、通信机制、部署形式和技术供应商。审查要确认业务策略没有知道不应知道的细节，技术选择变化时核心业务不必跟着修改。

### 4.3 保留选择但不建设未来插件系统

重要但尚无必要立即决定的技术选择，应尽量推迟。保留选择不等于为所有未来建立复杂插件系统。只有高概率变化、替换代价高、供应商绑定风险真实存在或已经形成架构边界的地方，才值得付出解耦成本。

## 5. Information Hiding 与 Deep Module

每个 Module 应隐藏一组设计知识和实现决策。调用者只需要知道它能做什么、如何正确使用，不应必须知道内部算法、存储结构、第三方实现、内部协作过程或无关配置。

优秀的 Deep Module（深模块）通常具有：

```text
简单接口 + 较强能力 + 隐藏较多内部复杂性
```

警惕 Shallow Module（浅模块）：接口已经很复杂，但几乎没有隐藏复杂性。每增加一个 Class、Interface、Method、Layer、Adapter 或 Wrapper，都必须隐藏或消除比自身带来的概念更多的复杂度，否则不要增加。

### 5.1 接口与 Contract

好的接口应小、稳定、意图清楚、隐藏实现、覆盖常见使用方式，并且不暴露无关能力。Contract 不只是类型签名，也包括调用者必须知道的行为约束。

警惕：

- 调用顺序只能靠记忆；
- 隐藏前置条件；
- 巨型接口；
- 调用者被迫知道不用的能力；
- Database Model、Framework 类型或第三方 SDK Object 直接穿过核心边界；
- 一个 Selector 或参数实际暗示多个独立职责。

隐藏调用顺序时，优先检查是否可以让一次调用具备完整语义，或把非法状态变成无法构造的状态，而不是只增加文档。

### 5.2 跨边界数据

跨架构边界的数据结构应简单、独立，只包含边界真正需要的数据。避免直接传递 ORM Entity、Database Row、Framework Request / Response、外部 SDK Object 或不必要的内部 Domain Entity。

不要因为两个模型字段相似就强行合并；它们可能拥有不同职责、生命周期、变化原因和变化速度。

### 5.3 Observable Behavior 与 Hyrum’s Law

稳定 Contract 不只包括文档中写出的接口。Hyrum’s Law（海勒姆定律）提醒我们：当使用者足够多时，系统所有可观察行为都可能被依赖，包括返回顺序、错误类型、默认值、时间行为、日志 / 事件、序列化格式和资源限制。

审查公共 Contract、配置、数据库 Schema、CLI、日志、事件或 API 变化时，应区分：

- 明确承诺的行为；
- 当前实现中可观察但尚未承诺的行为；
- 可以安全改变的内部细节。

如果变化可能影响下游消费者，应先进行影响发现，记录兼容策略、Deprecated 方式、迁移路径和回滚限制。不要仅因为某个行为没有写进文档，就假定它没有消费者。

## 6. 模块边界与过度拆分

小类、小函数和更多层不自动等于好设计。判断边界时重点看“修改原因”和“隐藏的知识”，而不是机械看文件长度、方法数量或类数量。

警惕：

- 大量只有转发作用的 Class；
- Pass-through Method（透传方法）；
- Wrapper 套 Wrapper；
- `Service → Manager → Handler → Adapter`，但没有新的 Contract、模型转换或策略；
- 相邻层接收同样参数、原样转发、调用下一层；
- 一个简单行为必须跨越很多文件才能理解；
- 多个模块高度耦合、无法独立理解、也没有隐藏不同知识。

相邻层存在的理由应至少是隐藏一种复杂性、转换一种模型、实施一种策略或建立一个真实边界。没有这些价值的空层应考虑删除或合并，而不是为了满足“分层架构”继续增加。

### 6.1 下沉复杂性

与模块职责密切相关、无法避免的复杂性，优先由模块内部承担，以显著简化调用者和接口。但不要无限下沉；只有当复杂性确实属于该模块、能显著降低调用者负担并使 Contract 更简单时，才这样做。

目标不是每个 Module 内部都最简单，而是整个系统总复杂度最低。

## 7. Testability、Failure 与状态

核心业务和 Use Case 应能在不启动 Web Server、真实 Database、Framework 或真实第三方服务的情况下验证。可测试性不是架构唯一目标，但它是判断解耦是否成立的重要证据。

审查至少覆盖：

- 正常行为和核心不变量；
- 边界、异常和重要分支；
- 依赖失败、超时、空结果和重试；
- 生命周期、状态变化和调用顺序；
- 授权、数据范围、SQL Safety 和 Fail Closed；
- Software Test、Integration Test、AI Evaluation 和 Business Acceptance 的分工。

如果测试一条业务规则必须启动大量外围设施，通常说明边界或依赖方向需要重新检查。但不要为了追求单元测试而制造脱离真实 Contract 的假抽象。

## 8. Optionality、演进与 Strategic Design

设计应随着真实变化、真实复用、真实依赖和真实维护成本逐步演进，不应在项目第一天设计最终组件图。提前猜测所有未来需求通常会制造错误抽象；但已经明确的核心边界和重要变化轴，应在设计阶段主动保护。

Strategic Design（战略式设计）不是大规模预设计。每次重要改动都应问：这次设计是否让下一次合理变化更困难？不要长期用局部补丁积累复杂度，也不要以“未来可扩展”为理由建立当前没有使用者的扩展点。

### 8.1 Design Twice

对会影响稳定边界、公共 Contract、依赖方向、供应商绑定或高成本未来变化的重要决策，不要直接采用第一个可行方案。至少比较一个真正不同的方向，比较：

- 复杂度和认知负担；
- 边界与依赖方向；
- 可测试性；
- 修改范围和影响可预测性；
- 接口复杂度；
- 当前实现成本；
- 未来合理变化成本。

Design Twice 是为了避免把“第一个想到的方案”误认为“正确方案”，不是要求每个小改动都写长篇设计文档。

### 8.2 可复查的决策

重要设计决策应记录：目标、约束、选择、替代方案、取舍、决策 Owner 和未来需要重新检查的信号。数据、依赖、用户规模、成本或技术约束变化后，允许重新评估原决策；“已经决定过”不是永久正确的证据。

### 8.3 Deprecation 与 Migration 是设计的一部分

对于预计会被替换或删除的 Module、API、数据格式、供应商或部署机制，Design Review 应至少询问：

- 消费者如何被发现；
- 是否能先 Expand，再逐步 Migrate，最后 Contract；
- 谁拥有迁移和删除责任；
- 如何设置可观察的 Milestone 和 Done When；
- 如何阻止新的旧用法继续进入；
- 哪些步骤可回滚，哪些变化不可逆。

这不要求所有设计都建立完整插件系统或迁移平台；只有真实存在替换成本或下游消费者时才增加这些设计。

## 9. Overengineering Guard

默认禁止以下机械做法：

- 每层一个 Interface；
- 每个外部调用一套复杂抽象体系；
- 每个 Feature 新建一层；
- 为所有未来实现预留 Plugin Point；
- 为了 Clean Architecture 强制增加无意义目录；
- 为了 DIP 创建没有替换价值的 Interface；
- 把所有 Class 拆得越小越好；
- 为“企业级”引入不需要的基础设施；
- 因为代码相似就提前抽象；
- 因为某个模式流行就重塑当前边界。

每个新增设计元素都必须回答：

1. 它隐藏了什么复杂性？
2. 它隔离了什么真实变化？
3. 它减少了谁的认知负担？
4. 它是否比自身带来的复杂度更有价值？

回答不出来，就不要新增。发现过度抽象时，推荐最小删除、合并或恢复直接调用的改进，并说明对 Contract 和测试的影响。

## 10. Review 输出与证据标准

不要看到问题立即重构。每个发现必须包含：

```text
Signal
→ 发现了什么设计信号

Evidence
→ 代码、Module、依赖、Spec 或 Contract 中的具体事实

Impact
→ 实际造成的 Change Amplification、Cognitive Load、Unknown Unknowns、Coupling、Testability 或 Maintainability 成本

Recommendation
→ 最小可行改进；如果会改变已确认的边界或 Contract，返回 Design Review / Spec 阶段
```

不要仅因为不符合某个模式、不够“Clean”、没有 Interface、Repository、Service 或微服务，就判定架构存在问题。没有实际影响的偏好不是 Finding。

## 11. 最终判断清单

好的架构应同时满足：

- **Business-Centered**：系统首先表达业务和 Use Case；
- **Policy-Protected**：高层策略不被低层细节污染；
- **Dependency-Controlled**：依赖方向明确并指向更核心、更稳定的部分；
- **Change-Localized**：常见变化限制在少数相关 Module；
- **Deep**：简单接口隐藏有价值的复杂性；
- **Cohesive**：因相同原因变化的内容聚集；
- **Decoupled**：因不同原因变化的内容可以独立演进；
- **Predictable**：修改影响范围容易预测；
- **Testable**：核心行为能够脱离外围设施验证；
- **Optional**：不必要的技术决定可以推迟；
- **Simple**：没有超过当前需求所必需的架构复杂度。

最高判断不是“是否符合 Clean Architecture”或“是否用了很多抽象”，而是：

> 它是否让重要业务更受保护，让细节更容易替换，让变化更局部，让系统更容易理解，让影响范围更容易预测，同时没有引入超过收益的不必要复杂性？
