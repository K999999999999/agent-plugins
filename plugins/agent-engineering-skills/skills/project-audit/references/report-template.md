# 项目审计报告模板

按项目规模裁剪篇幅，但下列证据和覆盖字段不可省略；只有全面审计一种运行模式。无发现可写“已检查范围内未发现”，不填充虚构问题。发现标注已确认 / 疑似 / 未验证；不适用项说明原因。报告默认在会话输出，不因使用模板就创建仓库文件。

## 1. 基线、目标与覆盖

- 仓库、分支、Commit、索引与工作区内容标识、未跟踪文件快照、时间；基线变更及重审情况。
- 项目当前目标、交付阶段、支持范围、事实源及仍待确认的假设。
- 全仓资产清单与逐文件台账的持久化位置；分类 / 免读依据、不可访问资产及执行限制。不得用抽样替代全量审查。

| 覆盖指标 | 数量 / 分母 | 说明 |
| --- | --- | --- |
| Git 受控路径、必要未跟踪 / 忽略文件 | 分别统计 | 与清单及台账对账；子模块分列，防止重复计数 |
| 人工全读目标、其他资产 | 分别统计 | 其他资产按生成物、第三方、二进制、文档等分类，说明处理情况 |
| 完整阅读、人工语义审查完成 | 分别统计 / 人工目标总数 | 同时满足两者且结论未失效的目标数及覆盖率 |
| 部分阅读、未读、阻塞、失效及其他未完成项 | 分别统计 | 提供完整路径列表或台账索引、原因和下一批 |
| 静态分析 | 各状态数量 | 通过 / 失败 / 未运行 / 阻塞 / 不适用及适用分母 |
| 运行验证 | 各状态数量 | 通过 / 失败 / 未运行 / 阻塞 / 不适用及实际证明范围 |

逐文件状态字段使用 [audit-checklist.md](audit-checklist.md) 的“文件台账与进度记录”；不能用下方模块汇总代替文件台账。目标数为零时覆盖率写不适用，不把免读和不适用计为通过。

| 领域 / 目录或业务链路 | 状态（已查 / 部分 / 未查 / 不适用） | 已读文件 / 调用链 | 验证方式及证据 | 缺口 / 原因 |
| --- | --- | --- | --- | --- |

模块表区别目录盘点、人工语义审查、静态分析和运行验证；注明跨模块复核是否完成及其证据。补充实际架构、调用关系、接口契约、核心业务流程、数据一致性，以及需求 → 实现 → 测试 → 部署的对应关系。

## 2. 整体评价与交付就绪

分别报告审计状态与交付状态。存在未完成审查的目标文件时必须写 **“审计尚未完成”**，列出剩余数量、路径、原因、后续批次；不得宣称全量审查结束。全部文件已审仍须说明跨模块复核及验证限制是否满足完成门禁。

综合功能完整性、系统架构、契约、数据一致性、安全、可靠性和维护成本，说明哪些目标已达到、哪些被阻塞、证据是否足够。交付结论选择继续优化 / 满足明确条件后冻结或交付 / 当前目标下可冻结或交付 / 证据不足暂不能判断，并标注可信程度。不要给无依据的质量分数，不把未验证当成通过。明确完整阅读不证明没有 Bug，测试通过不证明代码逻辑完全正确；结论仅针对所列基线、证据与支持范围。

## 3. 已确认的问题（P0 → P3）

每项包含：

- ID、标题、优先级及其实际影响依据。
- 状态：已确认；可信程度：高 / 中 / 低，并解释证据强弱。
- 基线对应的 `文件:行号`，以及运行证据或可达调用链；标注静态确认 / 已复现。环境问题使用具体命令、配置及脱敏输出定位。
- 触发条件、受影响目标 / 用户 / 数据和已有防护为何不足。
- 推荐的最小处理方式、保留或延期的代价、处理后的验证方法。

同根因合并，避免一个缺陷拆成多个问题。

### 疑似问题

逐项列出位置、候选风险优先级及依据、现有证据、反证与待核实条件；不得使用已确认语气。没有则明确写无。

### 未验证内容

逐项列出未完成文件、未决契约 / 链路、未运行检查、环境或权限限制、对系统及交付判断的影响和最小验证方法；明确哪些需要额外授权。没有则明确写无。

## 4. 冗余与过度工程专项

| 候选 / 位置 | 状态及证据 | 职责、调用方与独有价值 | 方案与简化收益 | 删除 / 兼容风险 | 验证方式 |
| --- | --- | --- | --- | --- | --- |

可填“保留”，不能为表格凑删除建议。对无明显冗余的项目说明已检查的入口、脚本、抽象和测试范围。

## 5. 测试、评测与部署的真实状态

| 类型 / 命令 | 环境、版本与输入 | 证据来源（已有测试 / 历史或 CI / 本次执行） | 结果与退出状态 | 实际证明范围及限制 |
| --- | --- | --- | --- | --- |

分别说明单元 / 集成 / Mock / E2E、AI Evaluation、构建与部署；未执行则写未执行和原因。失败区分产品缺陷、基线失败和环境阻塞，无法判断时不猜测。记录真实 LLM / 外部服务是否调用及授权范围；未部署或未访问环境不能声称部署通过。

## 6. 值得保留的设计

列出有证据支持、符合当前目标的设计与不应修改的理由；允许结论为保持现状，不制造抽象、拆分、测试或平台建设任务。

## 7. 建议、延期项与停止点

- 当前最值得处理的少量问题，关联发现 ID、收益及验证条件；无必要动作则明确说明。
- 可以延期、无需处理或仅待验证的事项及理由。
- 冻结 / 交付的阻塞条件、残余风险和判断边界；存在关键证据缺口时列出所需最小验证，而非无限优化清单。
