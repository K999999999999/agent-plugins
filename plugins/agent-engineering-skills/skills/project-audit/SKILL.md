# 项目全面审计

判断项目是否真正实现当前目标、有哪些现实风险，以及是否值得继续优化。以项目规模、支持范围和交付目标为标准；复杂度、文件数量和工具数量都不是专业程度的证明。

## 模式与边界

- `overview`：快速体检，优先核对目标、核心链路和高影响风险；明确抽样范围，不声称全面覆盖。
- `full`：分阶段盘点全仓、还原链路、逐领域审查、交叉验证和汇总；持续跟踪覆盖范围。至少考虑 [audit-checklist.md](references/audit-checklist.md) 中全部维度，不适用项注明原因。
- `focused`：深入用户指定领域，追踪必要的跨模块调用与依赖；其他领域列为范围外。

用户未指定模式时按请求选择并说明：快速体检用 `overview`，全面审计用 `full`，指定领域用 `focused`。普通问答不启动全面审计。目标或范围缺失时先查仓库事实；仍有影响结论的歧义则询问，同时继续不依赖答案的只读盘点。

默认只读，不自动修复、重构、删除文件、提交 Commit、Push 或创建 PR。报告默认在会话中输出；写入仓库须有用户授权。保留用户已有修改，不回退或清理工作区。

## 核心流程

1. **建立基线**：读取适用的 `AGENTS.md`、README、Spec / Ticket、ADR 和运行说明；记录仓库路径、分支、Commit、工作区状态、审计时间、模式、项目目标、交付阶段及支持范围。工作区有修改时明确结论针对哪个快照，不能只标 Commit。找不到明确目标时标注推定与待确认项，不自行发明验收标准。
2. **盘点全仓**：结合 `git ls-files`、`rg --files --hidden` 和按需检查忽略规则，识别应用入口、模块、依赖、脚本、配置、测试、文档、CI、构建和部署链路。目录清单不等于已审查实现；记录排除的生成物、第三方代码、忽略目录、子模块及不可访问部分，避免读取或展示秘密文件内容。维护轻量覆盖表：领域 / 目录或链路、已读证据、静态审查或运行验证、待查项与限制。
3. **还原架构与业务**：从真实入口追踪输入、认证授权、业务处理、持久化、外部调用和输出，覆盖核心成功、失败及边界路径。核对实际配置选择了哪个实现，区分可达功能、占位实现、Mock / 演示路径与未接入代码，不能只凭 README、文件名或函数存在认定功能完成。
4. **分领域交叉检查**：按适用维度读取 [audit-checklist.md](references/audit-checklist.md) 的相关部分，结合实现、调用方、依赖与测试，核对需求 → 入口 → 实现 → 断言 → 部署配置是否一致。`full` 按模块或风险分批推进，更新覆盖表；中断时报告已查、待查及下一阶段，不将阶段性结论写成全量验收。
5. **核实发现**：为候选问题追踪触发条件、调用链和反证，检查是否已有保护、替代实现或范围约束。对疑似重复、废弃代码或过度设计，核查真实职责、所有调用方（含脚本、配置和动态加载）、独有价值、删除风险、替代方案与简化收益；搜索无引用或代码相似均不足以确认可删。
6. **安全验证**：先阅读命令、脚本和 Fixture 的副作用，再在已有授权范围内执行本地、隔离、确定性的检查。真实 LLM、付费接口、破坏性命令、环境或数据修改必须事先有明确授权；不得因“测试”名称而默认获准。普通临时测试产物仅可放入已授权的隔离临时位置；不能隔离副作用就不运行。不得擅自安装依赖、启动共享服务、迁移数据库或部署。无法运行则记录原因和待验证方法，继续可做的静态审查。命令、日志和报告中的凭证、个人信息与业务数据须脱敏。
7. **形成结论**：使用 [report-template.md](references/report-template.md) 汇总，按模式调整篇幅但保留基线、覆盖限制、证据状态和交付判断。合并同根因发现，只推荐少量最有价值的动作；已有设计合理且无现实问题时明确建议保持现状。

## 证据与停止条件

- 所有结论标为 **已确认 / 疑似 / 未验证**，问题同时说明可信程度及依据。静态证据足够证明缺陷时可确认，但注明未复现；无法确认的候选不得混入已确认问题。
- 问题提供基线对应的 `文件:行号`、运行证据或可达调用链、实际影响、推荐处理方式和验证方法。没有可定位代码的环境问题用具体配置、命令与脱敏输出定位，不编造行号。
- 严重度按实际影响和触发条件判定：P0 为正在发生或可直接触发的灾难性损失 / 关键安全事故；P1 为核心目标或交付阻塞、重大安全或一致性问题；P2 为明确但有限的功能 / 可靠性 / 维护问题；P3 为低影响且可延期事项。缺少某项工具或某类测试本身不构成缺陷。
- 区分“仓库已有测试”“历史 / CI 记录”和“本次实际通过”，记录命令、环境、退出状态及覆盖范围；Mock 通过不证明真实集成、AI 质量或生产就绪。无法遍历、运行或访问的部分必须显式列出，禁止将静态检查包装为完整运行验收。
- 不编造检查结果、测试通过记录、质量分数或问题。未发现问题只说明已检查范围内未发现，不能推出系统无缺陷。
- 不为完成清单制造工作。适用范围已检查、关键疑点已验证或明确受限后停止；区分继续优化、满足明确条件后冻结 / 交付、当前目标下可冻结 / 交付、证据不足暂不能判断。说明阻塞项和残余风险；审计判断不授权实际发布。

## 与已有 Skill 协作

本 Skill 汇总项目级证据和优先级，不复制以下 Skill 的完整流程，也不自动调用它们或扩大授权：

- `workflow-code-review`：审查已有 Diff 对 Spec / Ticket 的符合性；不能用项目审计替代本次变更 Review。
- [diagnosing-bugs](../diagnosing-bugs/SKILL.md)：需要专门复现、最小化或定位根因时，提出独立诊断建议。
- [improve-codebase-architecture](../improve-codebase-architecture/SKILL.md)：需要进一步探索架构摩擦和模块改进候选时使用；审计仅报告与目标相关的架构风险。
- [maintainability-refactor](../maintainability-refactor/SKILL.md)：问题与目标明确且用户授权重构后使用；审计不给出实施授权。

其他 Plugin 未安装时保留建议，不把它作为完成审计的依赖。默认以中文输出，保留技术术语、代码标识和原始命令。
