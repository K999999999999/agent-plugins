# 项目全面审计

判断项目是否真正实现当前目标、有哪些现实风险，以及是否值得继续优化。以项目规模、支持范围和交付目标为标准；复杂度、文件数量和工具数量都不是专业程度的证明。

## 单一运行模式与边界

全面审计 = 全仓资产覆盖 + 全量人工源码审查 + 跨模块分析 + 实际验证 + 系统级质量判断。只有这一种运行模式，不提供快速、抽样或专项替代模式。用户强调某领域时可以调整批次优先级，但不能缩小全面审计范围；时间、上下文或工具受限时交付阶段性结果并明确尚未完成。

普通问答不启动全面审计。目标缺失时先查仓库事实；仍有影响结论的歧义则询问，同时继续不依赖答案的只读盘点。

默认只读，不修改被审计仓库，不自动修复、重构、删除文件、提交 Commit、Push 或创建 PR。报告默认在会话中输出；持久化台账放在被审计仓库之外的可写位置并告知位置，写入仓库须有用户授权。保留用户已有修改，不回退或清理工作区。

## 核心流程

1. **建立基线**：读取适用的 `AGENTS.md`、README、Spec / Ticket、ADR 和运行说明；记录仓库路径、分支、HEAD Commit、工作区状态、审计时间、项目目标、交付阶段及支持范围。除 Commit 外保存索引对象标识、工作区文件内容摘要及新增 / 删除状态，覆盖纳入审计的未跟踪文件，确保结论对应可识别的快照。敏感内容只记录安全摘要或受保护的标识，不复制秘密。找不到明确目标时标注推定与待确认项，不自行发明验收标准。
2. **盘点全仓**：用 `git ls-files -z` 枚举所有受控路径，以 `git status --porcelain=v1 -z --untracked-files=all` 记录暂存、未暂存、删除和未跟踪状态；用 `git ls-files --others --exclude-standard -z` 补充未跟踪清单。按 NUL 分隔处理路径，避免空格或换行导致遗漏。按需检查忽略规则，纳入必要的未跟踪 / 忽略配置、运行输入或本地实现；不能仅用 `rg --files` 代替 Git 清单。为每个受控文件和必要的未跟踪文件建立台账，识别入口、模块、依赖、脚本、迁移、配置、测试、文档、CI、构建及部署资产。分类、排除依据和文件级字段见 [audit-checklist.md](references/audit-checklist.md) 的“文件台账与进度记录”。目录清单不等于已审查实现。
3. **完整逐文件审查**：按模块、依赖和风险分批，但必须完整阅读并审查所有人工编写的源码、测试、脚本、数据库迁移和重要配置，包括隐藏目录、CI、构建及部署文件。大文件分段读取，记录连续已读范围并检查输出截断；覆盖全文且完成语义审查后才可标为完成。不得以抽样、搜索命中、签名、文件头、摘要、扫描或测试通过代替完整阅读。逐文件分析逻辑正确性、边界条件、异常及资源处理、安全性、可维护性、重复实现和不必要复杂度。测试审查断言、隔离、Mock 和遗漏路径；迁移、脚本及配置审查副作用、执行顺序、兼容与失败恢复。文档和其他资产按职责逐文件核对。跨文件疑点记录待追踪项。
4. **持久化批次进度**：每批结束、切换上下文或中断前保存台账、发现、未决调用链、验证记录和下一批路径。恢复时先读持久化记录并核对基线及内容摘要，再从未完成范围继续；不得依赖会话记忆或仅凭旧结论跳过变更文件。无法持久化时明确进度恢复限制。阶段报告列出已查、待查及下一批，不得写成全量验收。
5. **跨模块与系统分析**：逐文件阶段可以先还原调用图，但全部目标文件审查后仍须单独完成系统级复核。从真实入口追踪输入、认证授权、业务处理、持久化、外部调用和输出，覆盖成功、失败、边界和状态转换。覆盖所有模块及其交互，包括动态注册、后台任务、脚本、迁移和部署链路；验证调用关系、参数 / 返回值 / 错误契约、业务流程、数据所有权与一致性、事务 / 幂等 / 并发、依赖方向及架构职责。核对配置选路，区分真实可达、占位、Mock / 演示和未接入实现。结合调用方、实现、依赖与测试，核对需求 → 入口 → 实现 → 断言 → 部署配置；考虑 [audit-checklist.md](references/audit-checklist.md) 的全部维度，不适用项注明原因。为模块及关键链路记录证据和未决项，不能凭 README 或函数存在认定功能完成。
6. **核实发现**：为候选问题追踪触发条件、调用链和反证，检查已有保护、替代实现或范围约束。对疑似重复、废弃代码或过度设计，核查真实职责、所有调用方（含脚本、配置和动态加载）、独有价值、删除风险、替代方案与简化收益；搜索无引用或代码相似均不足以确认可删。
7. **实际安全验证**：结合现有静态分析、测试和运行证据选择实际检查。先阅读命令、脚本、插件和 Fixture 的副作用，再在已有授权范围内执行本地、隔离、确定性的检查。真实 / 付费 LLM、付费接口、破坏性操作、环境或业务数据修改必须事先有明确授权；不得因“测试”名称而默认获准。产物、缓存、覆盖率和临时数据只放仓库外的隔离位置；工具必须写源码目录时在外部隔离副本执行并核对其基线。不能隔离副作用就不运行。不得擅自安装依赖、启动共享服务、迁移真实数据库或部署。无法运行则记录原因和待验证方法，继续独立静态审查。命令、日志和报告中的凭证、个人信息与业务数据须脱敏。
8. **复核基线与形成结论**：每批开始 / 结束、恢复及最终交付前核对 HEAD、索引、工作区状态、资产清单和内容摘要。新增、修改、删除、重命名或类型变化时，保留旧证据对应的快照、更新清单，使受影响的阅读 / 审查 / 验证结论失效；重新完整审查变更文件，复核相关调用方、契约、跨模块结论及测试。记录新旧基线和影响范围，不能把不同快照证据拼成一次完整审计；持续变化无法固定时明确尚未完成。使用 [report-template.md](references/report-template.md) 提供全仓覆盖统计、已确认问题、疑似问题、未验证内容、风险优先级和交付就绪结论。系统质量判断须综合目标完整性、架构 / 契约、数据一致性、安全、可靠性、维护成本和运行证据，不能仅汇总单文件意见。合并同根因发现，只推荐少量最有价值的动作；已有设计合理时建议保持现状。

## 证据与停止条件

- 每个文件分别记录完整阅读、人工语义审查、静态分析、运行验证及未完成原因；状态互不替代，不适用项说明理由且不能计入通过数量。
- 所有结论标为 **已确认 / 疑似 / 未验证**，问题同时说明可信程度及依据。静态证据足够证明缺陷时可确认，但注明未复现；无法确认的候选不得混入已确认问题。
- 问题提供基线对应的 `文件:行号`、运行证据或可达调用链、实际影响、推荐处理方式和验证方法。没有可定位代码的环境问题用具体配置、命令与脱敏输出定位，不编造行号。
- 严重度按实际影响和触发条件判定：P0 为正在发生或可直接触发的灾难性损失 / 关键安全事故；P1 为核心目标或交付阻塞、重大安全或一致性问题；P2 为明确但有限的功能 / 可靠性 / 维护问题；P3 为低影响且可延期事项。缺少某项工具或某类测试本身不构成缺陷。
- 区分“仓库已有测试”“历史 / CI 记录”和“本次实际通过”，记录命令、环境、退出状态及覆盖范围；Mock 通过不证明真实集成、AI 质量或生产就绪。无法遍历、运行或访问的部分必须显式列出，禁止将静态检查包装为完整运行验收。
- 不编造检查结果、测试通过记录、质量分数或问题。完整阅读全部文件不证明没有 Bug，测试通过也不证明代码逻辑完全正确；未发现问题只说明该基线及已检查范围内未发现。
- 只有资产清单闭合、全部目标文件完成适用审查、跨模块分析完成、适用验证已执行或限制已明确披露，才可报告审计工作完成。若仍有目标文件未完整阅读、未完成语义审查、不可访问或结论失效，必须明确写 **“审计尚未完成”**，列出数量、路径、原因和下一批；不得宣称全量审查结束。受限验证不能计为通过，影响关键判断时交付结论须为证据不足或附明确条件。
- 审计完成与项目可交付分别判断。不为清单制造问题；区分继续优化、满足明确条件后冻结 / 交付、当前目标下可冻结 / 交付、证据不足暂不能判断。说明阻塞项和残余风险；审计判断不授权实际发布。

## 与已有 Skill 协作

本 Skill 汇总项目级证据和优先级，不复制以下 Skill 的完整流程，也不自动调用它们或扩大授权：

- `workflow-code-review`：审查已有 Diff 对 Spec / Ticket 的符合性；不能用项目审计替代本次变更 Review。
- [diagnosing-bugs](../diagnosing-bugs/SKILL.md)：需要专门复现、最小化或定位根因时，提出独立诊断建议。
- [improve-codebase-architecture](../improve-codebase-architecture/SKILL.md)：需要进一步探索架构摩擦和模块改进候选时使用；审计仅报告与目标相关的架构风险。
- [maintainability-refactor](../maintainability-refactor/SKILL.md)：问题与目标明确且用户授权重构后使用；审计不给出实施授权。

其他 Plugin 未安装时保留建议，不把它作为完成审计的依赖。默认以中文输出，保留技术术语、代码标识和原始命令。
