# 诊断 Bug

用于处理报错、行为错误、测试失败、性能变慢和难以稳定复现的问题。核心不是一开始猜原因，而是先建立一个能捕获用户准确症状的紧反馈循环。

本 Skill 默认负责诊断和报告。只有用户明确要求修复，或当前任务的 Scope 已明确包含修复时，才进入修改代码和回归测试阶段。

## 安全和脱敏

诊断过程会展示命令、输出和捕获的日志。展示前必须脱敏：

- API Key、Token、Password、Connection String；
- Authorization Header、Cookie、Session；
- 个人信息、业务机密和真实数据；
- 能推断内部权限或基础设施的敏感路径和配置。

用 `<REDACTED>` 替换敏感值，凭证通过环境变量或安全配置注入，不要写入命令、日志、Ticket 或文档。如果脱敏后信息不足以定位问题，明确说明缺少什么并请求用户提供更小范围的安全样本。

默认只使用本地或隔离环境。不能未经明确授权添加生产埋点、修改生产数据、重启关键服务或执行破坏性操作。

## 开始前

读取与问题相关的事实源：

- `AGENTS.md` 或 `CLAUDE.md`；
- 相关本地 Spec / Ticket；
- `CONTEXT.md`、`CONTEXT-MAP.md` 和 ADR；
- 相关 Architecture、Module、Contract、代码、测试和运行配置。

先复述用户看到的准确症状、触发条件和影响范围。区分“实际观察到的事实”和“用户对原因的猜测”。

## Phase 1：建立反馈循环

这是整个诊断的核心。如果没有一个能针对本次 Bug 变红的信号，继续阅读代码和提出理论通常不会带来可靠进展。

按大致优先级寻找反馈循环：

1. 在能到达 Bug 的 Seam 上写一个失败测试；
2. 对开发环境运行 HTTP / API 脚本；
3. 用 Fixture 输入运行 CLI，并与已知正确结果比较；
4. 使用 Headless Browser 驱动 UI，并断言 DOM、Console 或 Network 行为；
5. Replay（重放）脱敏的请求、Payload、Trace 或事件日志；
6. 构造只覆盖 Bug 路径的临时 Harness；
7. 对输出不稳定的问题使用 Property / Fuzz 测试；
8. 对已知版本范围建立 Bisection（折半）检查；
9. 用旧版本与新版本或两种配置做 Differential（差分）比较；
10. 必须人工操作时，使用 `scripts/hitl-loop.template.sh` 保持步骤和观测结构化。

### 收紧反馈循环

得到第一个循环后继续收紧：

- 缩小初始化、Fixture 和测试范围；
- 断言准确症状，而不是只断言“不报错”；
- 固定时间、随机数、文件系统和网络；
- 缩短运行时间；
- 确保每次结果可重复。

一个几十秒且偶发的循环通常不够好；目标是一个秒级、确定、无人值守且真正能捕获该 Bug 的命令。

### Phase 1 完成条件

必须已经实际运行过至少一次一个明确命令，并保留脱敏后的调用和输出。这个命令必须同时满足：

- **Red-capable（可变红）**：确实经过该 Bug 的代码路径，并断言用户准确症状；
- **Deterministic（确定性）**：相同输入通常得到相同结论；非确定性问题需要提高复现率；
- **Fast（快速）**：通常为秒级，而非依赖长时间环境；
- **Agent-runnable（可无人值守）**：不依赖人工点击，除非通过 HITL 模板明确驱动。

如果无法建立循环，停止进入假设阶段，列出已经尝试的方式，并请求以下一种安全信息：

- 可复现问题的隔离环境；
- 脱敏的日志、HAR、Trace、Core Dump 或带时间戳的录屏；
- 明确授权添加临时观测点。

## Phase 2：复现并最小化

运行反馈循环，确认：

- 复现的是用户描述的失败，而不是附近的另一个错误；
- 多次运行都能复现，或非确定性问题已经达到可诊断的复现率；
- 已记录准确的错误、错误输出、慢在哪个阶段或其他症状。

然后逐个减少输入、调用方、配置、数据和步骤。每删一个元素就重新运行循环，只保留仍然使问题变红的部分。

最小化完成的标准是：剩余每个元素都不可再删，删除任意一个都会使循环变绿。不要为了最小化而删除真实业务约束、修改生产数据或覆盖用户文件。

## Phase 3：提出假设

在验证前提出 3–5 个按优先级排列的假设，避免被第一个看似合理的原因锚定。

每个假设必须可证伪，并写出预测：

```text
如果 X 是原因，那么改变 Y 应该使问题消失，或改变 Z 应该使问题更严重。
```

无法写出预测的内容只是感觉，不是可操作假设。向用户展示假设列表，让用户补充已知信息或重新排序；用户没有补充时，可以按当前排序继续，但不能把假设当成结论。

## Phase 4：观测和验证

每个 Probe（探针）必须对应一个具体假设和预测，并且一次只改变一个变量。

优先级：

1. Debugger / REPL 检查；
2. 在能区分假设的边界添加定向日志；
3. 不要“到处打日志再搜索”。

所有临时 Debug 日志使用唯一前缀，例如 `[DEBUG-a4f2]`，便于结束时精确清理。不要把敏感数据写入日志。

性能回归使用独立分支：先建立基线计时、Profiler、Query Plan 或其他测量，再定位和修复。不要用大量日志替代性能测量。

## Phase 5：修复和回归测试

只有用户明确要求修复或任务 Scope 包含修复时，才进入本阶段。

如果存在正确的测试 Seam：

1. 将最小复现转换为该 Seam 上的失败回归测试；
2. 确认测试确实变红；
3. 用最小修改修复根因；
4. 确认回归测试变绿；
5. 重新运行原始的、未最小化的反馈循环。

正确的 Seam 必须复现真实 Bug 模式。如果只有过浅的单调用测试，而 Bug 需要多调用方协作，使用这样的回归测试会制造虚假信心。

如果没有正确 Seam，这是一个架构发现：当前代码形状阻止了可靠回归。记录它，并返回 `codebase-design` 或 Spec / Ticket 流程单独处理，不要为了测试方便暴露内部结构。

## Phase 6：清理

完成前必须确认：

- 原始复现循环已经不再复现；
- 回归测试通过，或已经记录不存在正确 Seam 的原因；
- 所有 `[DEBUG-...]` 临时日志已移除；
- 本次创建的临时 Harness 或 Prototype 已删除，或移动到明确标记的诊断目录；
- 不删除用户原有文件或无关产物；
- 已确认的根因和剩余风险已经写入诊断报告；
- 如果发生了实现修复，根因可以写入对应本地 Ticket 的 Result 或 Commit message，不依赖 PR。

## 诊断报告

用以下结构报告，不要只给一个未经证实的猜测：

```md
# Bug Diagnosis

## Symptom

用户实际观察到的症状和影响。

## Reproduction

复现命令、输入、环境和脱敏后的结果。

## Minimised Case

仍然能复现的最小场景。

## Hypotheses

每个假设、预测、验证动作和结果。

## Root Cause

已经被证据支持的根因；如果尚未确定，明确写“未确定”。

## Fix and Regression

是否按授权修复、回归测试和验证结果。

## Remaining Risk

未覆盖的环境、数据、性能或架构风险。
```

默认使用中文。Skill 名称、命令名、API、类名、函数名、文件路径、代码和必要的原始术语保持原样。
