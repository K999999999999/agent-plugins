# Research

使用 Research 调查一个会影响设计、实现或决策的事实问题。输出不是搜索结果堆积，而是一份能被后续 Spec、ADR 或实现引用的本地证据记录。

## 什么时候使用

适合：

- 查阅第三方 API、Library 或平台的实际能力；
- 确认当前版本的官方行为、限制和兼容性；
- 阅读标准、规范、论文或一手源码；
- 比较少量方案并记录事实依据；
- 当前仓库之外的信息是继续决策的前置条件。

不适合：

- 只是想了解当前仓库已有代码；
- 需求或术语还没有澄清；
- 用搜索结果替代本地代码和项目事实源；
- 为了支持已经选定的方案而只挑有利证据。

## 研究原则

- **一手资料优先。** 使用官方文档、官方源码、标准、规范、第一方 API 文档和原始论文；技术问题不要只引用博客、转述文章或搜索摘要。
- **版本必须明确。** 记录 Library、API、平台和文档对应的版本或访问日期；不把旧版本行为当成当前事实。
- **事实与推断分开。** 明确哪些内容由来源直接支持，哪些是基于多个事实得出的推断。
- **每个关键结论都有来源。** 使用 Markdown 链接引用具体页面、章节、源码位置或规范条款。
- **只研究当前问题。** 不无限扩展相关背景，也不为未来假设建立资料库。
- **不抄长文。** 用自己的话总结，保留足以验证结论的短摘录和精确链接。

## 执行流程

### 1. 定义问题

先写清楚：

- 需要回答的一个问题；
- 研究范围和排除范围；
- 需要支持哪个 Spec、ADR、Contract 或设计决定；
- 需要的版本、运行环境和时间点；
- 什么结果才足以解除当前阻塞。

问题过宽时，先拆成少量可独立回答的子问题，但不要把研究变成没有终点的清单。

### 2. 读取本地事实

先读取与问题相关的：

- `AGENTS.md` 或 `CLAUDE.md`；
- `CONTEXT.md`、相关 ADR 和现有 Spec；
- `pyproject.toml`、`package.json`、Lockfile 或实际版本信息；
- 相关代码、测试和已有研究记录。

不要研究已经能由当前仓库直接确认的内容。若本地版本与外部最新文档不同，以任务要求的版本和仓库实际配置为准，并记录差异。

### 3. 查找和验证来源

按以下顺序查找：

1. 当前版本的官方文档和发行说明；
2. 官方源码、类型定义、测试和 API Schema；
3. 标准、规范和原始论文；
4. 第一方维护者的明确说明。

对于关键结论，尽量使用两个相互独立的一手证据，或说明为什么一个权威来源已经足够。记录来源标题、链接、版本 / 日期和支持的结论。

优先查找问题中的精确术语、版本和 API 名称。不要仅凭搜索摘要判断限制、默认值或兼容行为。

### 4. 使用独立研究上下文

如果运行环境支持独立 Research Worker，可以让它负责资料搜集，同时保留主会话处理仓库决策。Worker 必须遵循本 Skill 的一手来源、版本和引用规则。

如果没有独立 Worker，在当前上下文完成研究，仍然使用相同的证据记录格式。不要为了并行而拆出无法独立验证的片段。

### 5. 形成结论

每个子问题都给出：

- 结论：当前能确定什么；
- 证据：哪些来源直接支持；
- 推断：基于证据得到的工程含义；
- 限制：尚未验证、版本相关或依赖环境的部分；
- 对当前项目的影响：是否改变 Spec、ADR、Contract 或下一步。

如果资料互相冲突，展示冲突并说明优先级，不要悄悄选择更方便的答案。

## 本地输出

默认写入：

```text
.scratch/research/<topic-slug>.md
```

如果仓库已经有明确的 Research 目录，优先复用现有约定。目录不存在时按需创建。不要写入外部 Issue、PR 或远程 Tracker。

## 研究记录模板

```md
# {研究主题}

研究日期：{YYYY-MM-DD}
目标版本 / 环境：{版本和环境}

## 问题

{需要回答的问题。}

## 范围

### 包含

- {范围}

### 不包含

- {排除项}

## 结论

{直接回答问题的简短结论。}

## 证据

| 结论 | 一手来源 | 版本 / 日期 | 说明 |
| --- | --- | --- | --- |
| {结论} | [{来源标题}]({链接}) | {版本 / 日期} | {来源支持的事实} |

## 工程影响

{对当前 Spec、ADR、Contract、实现或测试的影响。事实与推断分开。}

## 限制与未决问题

- {尚未验证或依赖环境的内容}

## 来源

- [{来源标题}]({链接})：{具体章节、源码位置或规范条款}
```

研究完成后报告文件路径、核心结论、主要来源和仍然存在的限制。不要自动修改代码、创建 Ticket 或提交外部任务。

默认使用中文。来源标题、API、类名、函数名、文件路径、代码和必要的原始术语保持原样。
