# Logic Prototype（逻辑原型）

Logic Prototype 用一个可分享、可点击的单文件 HTML，验证状态模型、业务逻辑、数据形状或状态转换。它适合回答“纸面上看起来合理，但实际推进几个场景后是否仍然合理”。

## 适用问题

- 状态机是否覆盖边界场景；
- 数据模型能否表示某种情况；
- 哪些动作在当前状态下合法；
- 一个 Interface 在正常和失败路径下应该返回什么；
- 用户点击或操作后，状态是否按预期变化。

如果问题主要是页面布局和视觉层级，使用 [UI.md](UI.md)。

## 流程

### 1. 写出问题

在 Demo 顶部的可见说明中写出：

- 当前要验证的状态模型或逻辑；
- 只回答哪一个问题；
- 需要观察哪些正常、边界和非法场景。

不要只把问题放在注释里。原型必须让用户在稍后返回时仍然知道它验证什么。

### 2. 隔离可迁移的逻辑

把回答问题的逻辑放在一个独立的 `<script>` 模块中，页面只是临时操作壳层。逻辑模块不得依赖 DOM、`document` 或按钮处理器；页面调用逻辑，逻辑不反向调用页面。

根据问题选择形状：

- **Pure Reducer（纯 Reducer）**：`(state, action) => state`，适合离散动作驱动的单一状态；
- **State Machine（状态机）**：显式列出状态和合法转换，适合“当前状态允许什么动作”本身就是问题；
- **Pure Functions（纯函数集合）**：没有隐式当前状态，只有对数据的转换；
- **带清晰方法面的 Class / Module**：逻辑确实拥有持续的内部状态时使用。

选择最能回答问题的形状，不要选择最容易接页面的形状。验证后的 Reducer、状态机或纯函数集合应该可以独立迁移到真实 Module。

### 3. 构建单文件 Demo

使用内联 HTML、CSS 和 JavaScript：

- 不使用 Framework、Bundler 或 Server；
- 能通过双击或一个简单命令运行；
- 操作标签使用领域语言，不暴露 Reducer、Action 等实现词汇；
- 不连接生产 Database、真实 API 或真实凭证；
- 每次操作后重新渲染完整相关状态，而不是只显示变化字段。

页面结构建议：

1. 标题和一行问题说明；
2. 当前状态面板，使用可读字段而不是只显示原始 JSON；
3. Free-play 按钮，每个按钮代表一个动作；
4. Guided Walkthrough，每个 Tab 代表一个可重复场景；
5. 场景应覆盖正常路径、困难边界和非法动作。

每次开始 Walkthrough 都重置到已知初始状态，每一步使用真实按钮推进，确保用户可以看到状态变化。

### 4. 交付原型

把文件路径或打开方式交给用户，让用户自由操作和运行 Guided Walkthrough。用户说“这个状态不应该出现”或“我原来以为会是另一种结果”时，记录为模型问题，而不是立即修改生产实现。

### 5. 记录结论

原型回答问题后，记录结论和关键场景。经过用户确认的状态规则进入目标仓库约定的 Spec；领域术语变化按 `domain-modeling` 处理。只有真实代码实现任务被确认后，才由 `workflow-implement` 重新实现并由 `workflow-tdd` 覆盖。

## 反模式

- 不为原型新增生产测试；
- 不连接生产 Database 或真实外部服务；
- 不把页面和逻辑揉成无法迁移的一团；
- 不添加未来假设的通用化能力；
- 不引入 Framework、Bundler 或 Server 来包装单一问题；
- 不把临时 HTML 壳层直接发布到生产环境。
