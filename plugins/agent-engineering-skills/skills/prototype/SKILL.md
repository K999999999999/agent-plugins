# Prototype

Prototype（原型）是为了回答一个明确问题而制作的临时代码或临时界面。问题决定原型的形状；原型不是生产实现，也不是提前完成 Feature 的借口。

## 选择分支

先根据用户问题、周边代码和目标判断：

- **“这个逻辑 / 状态模型是否合理？”** → 使用 [LOGIC.md](LOGIC.md)；
- **“它应该看起来怎样？”** → 使用 [UI.md](UI.md)。

如果问题确实含糊：

- 有后端 Module、状态模型或数据规则时，默认选择 Logic；
- 有现成页面或界面布局时，默认选择 UI；
- 在原型顶部明确写出这个假设；
- 不要同时制作两个分支来回避一个尚未确认的问题。

## 两个分支共有的规则

1. **从第一天就标记为临时。** 原型名称、路径和页面说明应让人一眼看出它不是生产代码。
2. **容易运行。** 提供一个清晰的本地运行方式，或让单文件可以直接打开；不要让用户先理解一套复杂环境。
3. **默认不持久化。** 状态放在内存中。只有问题本身研究持久化时，才使用隔离的临时 Database 或明确标记的本地文件。
4. **不追求生产级完整性。** 不写无关抽象、完整错误处理或生产级测试；只补足让原型可运行和可观察的部分。
5. **显示关键状态。** 每次操作后展示完整的相关状态，或在 UI 变体切换时明确显示当前变体。
6. **一次只回答一个问题。** 不添加“以后也许会需要”的能力。
7. **与生产代码隔离。** 不把原型直接当成生产实现；验证出的决定需要通过 `workflow-to-spec`、`workflow-tdd` 和 `workflow-implement` 按工程规则重新落地。

## 结束和固化

原型得到答案后，记录：

- 原型回答的问题；
- 用户选择的方案或得到的结论；
- 支撑结论的场景和观察；
- 尚未验证的风险。

将已经确认的决定整理进本地 `.scratch/<feature>/spec.md`，必要时由 `domain-modeling` 更新 `CONTEXT.md` 或 ADR。不要自动把原型代码合并到生产 Module，也不要自动创建外部 Issue / PR。

原型是否保留：

- 一次性原型默认放在临时目录或 `.scratch/<feature>/prototype/`；
- 用户明确需要复用时，才保留在本地分支或项目约定目录；
- 不删除用户原有文件；
- 不因为原型有效就把整个临时 UI 或临时壳层带进主实现。

默认使用中文。Skill 名称、命令名、API、类名、函数名、文件路径、代码和必要的原始术语保持原样。
