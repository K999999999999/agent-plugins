# Out-of-Scope 知识记录

`.scratch/out-of-scope/` 用于保存被明确拒绝、当前不进入项目范围的 Enhancement 决定。它的价值有两个：

1. 保存决定和理由，避免以后重复讨论；
2. 发现相似请求时提醒用户之前的边界。

## 目录结构

```text
.scratch/
└── out-of-scope/
    ├── {concept-a}.md
    ├── {concept-b}.md
    └── {concept-c}.md
```

一个概念使用一个文件，不要每个 Ticket 建一个文件。多个请求相同概念时追加到同一个文件。

## 文件格式

```md
# {概念名称}

当前项目不包含 {概念或能力}。

## 为什么不在范围内

{记录持久、具体的理由，包括项目范围、架构约束或经过确认的方案取舍。}

## 已确认的影响

- {如果实现该能力，需要改变什么}
- {为什么这与当前方向冲突}

## Prior requests

- `.scratch/{feature-a}/issues/{NN}-{slug}.md`
- `.scratch/{feature-b}/issues/{NN}-{slug}.md`
```

不要求固定章节数量；重点是让第一次看到这个概念的人理解决定和原因。

## 文件命名

使用简短、可识别的 kebab-case 概念名，例如 `{concept-name}.md`。不要使用工作项编号作为唯一文件名。

## 理由要求

理由应该是可长期成立的：

- 项目范围或产品方向；
- Architecture 或 Contract 约束；
- 明确选择了另一个方案；
- 数据、权限、安全或运行环境限制。

不要把“目前没时间”“以后再说”写成拒绝理由；这通常是延期，而不是 Out of Scope。

## 何时检查

Triage 新工作项时检查所有 `.scratch/out-of-scope/*.md`：

- 按概念相似度判断，不只匹配关键词；
- 发现相似记录时，先展示之前的理由；
- 询问用户当前请求是否仍然遵守该边界。

用户可以：

- **确认边界**：把新 Ticket 路径追加到 `Prior requests`，并将当前工作项标记为 `wontfix`；
- **重新考虑**：用户明确改变决定后，更新或移除记录，再进入正常流程；
- **区分概念**：保留原记录，当前请求继续正常 Triage。

## 何时写入

只有 Enhancement 被明确决定为 `wontfix` 时才写入。Bug 被拒绝时可以记录决定，但不要把所有 Bug 都当成产品范围排除项。

如果当前请求已经实现，不要写入这里；已实现能力不是被拒绝的能力，应在 Ticket 的 Result 中记录证据。

写入流程：

1. 用户确认当前 Enhancement 不在范围内；
2. 检查是否已有相同概念文件；
3. 有则追加本地 Ticket 路径；
4. 没有则创建概念文件，写入决定和持久理由；
5. 更新当前 Ticket 的 `Triage` 和 `Status`；
6. 保留当前工作项，不删除历史记录。

## 更新或移除

如果用户改变了之前的决定：

- 先确认新的范围和影响；
- 更新或移除对应概念记录；
- 当前新请求作为新的本地工作流继续；
- 不修改历史 Ticket 的正文和 Result。
