# 解决 Merge / Rebase 冲突

只在仓库已经处于 Merge 或 Rebase 冲突状态时使用。目标是保留双方有效意图，并让结果满足当前操作的目标、项目 Contract 和测试要求。

## 安全边界

- 先确认当前确实存在正在进行的 Merge / Rebase，不要在普通脏工作区中擅自开始合并；
- 不覆盖用户未纳入当前冲突的修改；
- 不使用 `git reset --hard`、`git clean`、强制覆盖或其他破坏性清理；
- 不自动执行 `merge --abort` 或 `rebase --abort`；
- 冲突意图无法判断时保留现场并询问，不编造新行为；
- 不从外部 PR、Issue 或远程 Tracker 推断解决方案；
- 不把解决冲突顺便扩展成重构、依赖升级或功能开发。

## 流程

### 1. 查看当前状态

只读检查：

- Merge / Rebase 状态；
- 冲突文件和冲突块；
- 当前 HEAD、操作目标和提交历史；
- staged、unstaged 和用户已有的无关修改。

确认当前操作是 Merge 还是 Rebase，以及它试图合入的目标。若状态不清楚，先报告，不要修改冲突文件。

### 2. 找到本地事实源

对每个冲突文件理解双方修改的原始意图，读取：

- 当前任务的本地 Spec / Ticket；
- `AGENTS.md` 或 `CLAUDE.md`；
- `CONTEXT.md`、`CONTEXT-MAP.md` 和相关 ADR；
- 两侧提交的本地 Commit message；
- 相关模块、Contract 和测试。

优先级通常是：已确认的 Architecture / Domain / Contract，其次是当前 Merge / Rebase 目标，最后才是单侧实现细节。不要仅凭“当前分支”或“新提交”判断哪一边必然正确。

### 3. 分析每个冲突块

对每个冲突块先判断它属于：

- 两侧对同一行为的不同实现；
- 一侧新增、另一侧删除；
- 同一 Contract 的兼容性变化；
- 格式、重命名或机械变化；
- 需要用户决定的真实产品或架构冲突。

如果两侧意图可以同时保留，合并它们并保持最小变化。如果不兼容：

1. 依据当前操作目标和已确认事实选择；
2. 记录为什么选择这一侧，以及舍弃了什么；
3. 如果选择会改变 Domain、Architecture、稳定 Contract 或数据语义，停止并请求确认。

不要简单选择“ours”或“theirs”，也不要为了消除标记而接受无法解释的结果。

### 4. 逐块解决

每解决一个冲突块，立即检查：

- 冲突标记是否删除；
- 语法、导入和类型是否仍然有效；
- 两侧需要保留的行为是否仍然存在；
- 是否引入未经确认的逻辑；
- 相关测试是否仍然适用。

不要在解决冲突时顺手做无关格式化或广泛重构，这会让结果难以审查。

### 5. 运行项目检查

发现所有冲突已解决后，读取项目规定的自动检查并依次运行适用项：

1. 语法、类型或静态检查；
2. 受影响的定向测试；
3. 完整相关测试套件；
4. 格式检查和 `git diff --check`。

测试失败时判断它是冲突解决造成的、原本就存在的，还是环境问题。修复只限于让当前合并结果满足原有 Contract；不要借机处理无关失败。

### 6. 完成当前操作

只有以下条件满足时才完成 Merge / Rebase：

- 所有冲突文件都已逐块审查；
- 冲突标记全部清除；
- 必需检查通过；
- 当前操作的结果符合 Spec / Ticket 和 Architecture；
- staged 内容只包含当前冲突解决相关文件。

对于 Merge，创建项目规定的本地 Merge Commit；对于 Rebase，按当前流程继续到结束。不要 Push、创建 PR 或修改外部任务。

如果无法安全完成，保留当前冲突现场，报告已分析的文件、未决冲突和需要用户决定的事项。

## 完成报告

```text
Status: PASS / BLOCKED
Operation: Merge / Rebase
Resolved: <文件或冲突块概况>
Tests: <检查结果>
Commit: <hash> <message> / None
Remaining: None / <未决冲突或风险>
```

默认使用中文。Git 命令、分支名、Commit SHA、文件路径、代码和必要的原始术语保持原样。
