# 全面审计检查项

每次全面审计均使用本清单。各领域记录实际资产、控制、运行证据、绕过路径及待验证项；按风险追踪具体实现，不以关键词命中代替核验。适用范围由项目事实决定，无 AI 功能的项目可将产品 AI Eval 标为不适用，但仍审查开发 Agent 的权限与质量门禁。

## 1. 需求、Spec、Ticket、验收和追踪

- 需求是否有权威来源、版本、Owner、范围与非目标；验收是否可观察，覆盖成功、失败、边界、安全及非功能要求。
- 需求 → Spec / Ticket → PR / Commit → 测试 / Eval → 发布是否能相互追踪；需求变更是否同步验收与回归检查。
- 验收者是否独立于生成实现的 Agent；含糊目标、占位实现或自造验收标准能否被发现。

## 2. 拆分、依赖、上下文和范围

- Ticket 是否形成可独立验证的交付片段，依赖是否明确，跨任务接口与迁移顺序是否有契约。
- 并行 Agent 是否共享可变工作区、分支或文件；冲突、陈旧上下文、重复修改和集成责任如何处理。
- 上下文恢复是否核对当前 HEAD、未提交改动、决策和未完成验证；是否用旧摘要代替项目事实。
- PR 是否混入无关重构、生成物或门禁降级；范围变化与风险升级是否触发重新验证和审查。

## 3. Agent 权限、工具、沙箱和授权

- 阅读本地 Skill、AGENTS.md、工具配置与执行策略，核对声明与实际运行边界。
- 文件系统、网络、Shell、凭证、GitHub App / Token 权限、生产和数据库访问是否符合任务最小需要；工作区、临时文件和秘密是否隔离。
- 不可信仓库内容、Issue、工具输出能否诱导越权执行或外传数据；工具是否把建议直接当授权。
- 提交、Push、修改门禁、合并、部署、付费调用和破坏性操作的执行身份及授权来源是否明确；同一身份是否能生成代码、降低门禁并合并。
- 区分提示词约定与运行时权限控制；没有沙箱不直接判严重缺陷，结合可达资源和授权边界评估。

## 4. 架构不变量、规范和结构检查

- 依赖方向、模块边界、接口兼容、数据所有权和禁止路径是否明确；机械规则能否由 Linter、类型检查、架构测试或 CI 执行。
- 设计性判断是否有清楚的规范及 Review 标准；高风险架构 / 数据决策是否要求明确授权或人工确认。
- 检查是否覆盖实际入口与新增模块，失败是否返回非零并阻断；是否存在只在文档中声明的“强制”约束。

## 5. TDD 与测试真实性

- 对要求 TDD 的流程查验行为失败 → 最小实现 → 重构的记录，不凭最终测试文件或 Commit 顺序断言执行过 TDD。
- 单元、集成、E2E 按风险承担什么责任，关键路径和失败恢复是否覆盖；不要求所有项目凑齐所有测试层。
- 断言是否验证需求、错误和副作用，还是只验证 Mock 自身、固定常量、快照或实现细节；替身是否掩盖真实接口问题。
- Fixture、时间、随机性、网络、数据库和状态是否隔离；空测试集合、测试发现失败或断言删除是否会被当作通过。
- 对历史缺陷检查修复前是否能失败；既有变异测试或失败注入可支持有效性判断，审计不默认新增执行。

## 6. 本地与 CI 的验证语义

逐项比较并填写报告矩阵：测试集合与断言、依赖锁和运行时、配置 / 数据库 Fixture、Mock / 真实依赖、跳过行为、隔离 / 缓存、构建与执行命令。

- 沿本地脚本 → CI 包装脚本 → 实际命令追踪参数、退出码、测试发现和覆盖范围；确认不是同名不同标准。
- 允许本地跑受影响测试、CI 跑完整确定性测试，前提是选择逻辑可靠且同一行为采用同一验收标准。
- 检查条件分支、OS / 时区 / Locale、环境变量、依赖版本漂移、缓存键和共享状态；CI 是否复用旧报告而不执行当前代码。
- 区分计划运行、实际运行、成功、失败、跳过和取消；定位本地成功而 CI 失败或反向漂移的根因。

## 7. AI Evaluation

- 建立变更风险 → Eval 要求映射：Prompt、RAG 检索 / 索引、Agent 工具 / 路由、Text2SQL 及确定性外围代码分别触发哪些验证；是否有可绕过的路径过滤。
- 测试集是否代表真实任务、错误类型及风险，有无泄漏 / 过拟合；标准答案、业务约束、数据版本和维护责任是否可靠。
- Eval 是否走真实目标链路，记录模型提供商 / 标识 / 版本、参数、Prompt、工具、索引、数据集、数据、代码 SHA 与运行环境；Mock 或替代链路不得冒充目标链路证据。
- Judge 是否以人工标注或已知正反例校准，是否偏好自身输出，如何处理分歧、漂移及低置信度；确定性判定能否替代不必要的 LLM Judge。
- PASS / FAIL / INVALID / 未执行 / 环境错误是否分别处理；缺报告、部分样本失败或环境失败能否被默认放行。
- 区分能力探索和正式回归门禁：探索结果不能自动成为稳定质量证明。门禁需有合理的重复次数、阈值、不确定性处理和风险容忍度。
- 审查采样随机性、稳定性、重试上限与选择性重试，不能挑选通过的一次覆盖失败；Token、费用、耗时、缓存有效性和执行预算是否可追踪。
- 报告复用必须绑定相容版本和输入；缓存命中不能掩盖新模型 / 索引 / 数据变化。审计只读现有报告，不调用付费模型补证。

## 8. Code Review

- 规范是否覆盖正确性、需求、边界、测试真实性、安全、架构及部署影响；Review 是否审查完整 Diff 及必要上下文。
- 审查者是否与作者共享身份、权限、上下文偏见或模型失败模式；独立身份本身不证明独立判断有效。
- 审批是否绑定当前版本，新增 Commit 后是否要求重新审查；作者、自动化或管理员能否自批、自合并或绕过。
- 从实际 Review 检查是否发现可定位的问题、是否修复和重新验证；仅机器人“LGTM”或评论数量不证明有效性。

## 9. 门禁自身的完整性

对每种路径追踪“谁可修改 → 谁审查 → 什么检测 → 什么阻断”，检查现有流程能否发现并阻止：

- 修改测试使错误通过、删除断言、降低阈值 / 覆盖率 / 验收标准、缩小 Eval 数据集或替换标准答案。
- 跳过失败测试、滥用 `skip` / `xfail`、宽泛捕获异常、吞退出码、`continue-on-error` 或只重试到通过。
- 改 CI 的事件、路径过滤、条件表达式、测试矩阵和作业依赖，使关键检查不运行，或让汇总检查忽略失败 / 未执行。
- 用旧 Commit、错误分支或不相容环境结果证明新版本；同名检查或不可信 App 伪造状态。
- 同一 PR 降低测试 / CI / 安全规则后仍自动合并；CODEOWNERS 是否实际被 required review 强制，而非只存在文件。

跳过或允许失败有合理用途时，核对其适用范围、理由、替代保障和有效期，不机械判缺陷。测试变更本身也不等于篡改；关键是语义变化、独立证据和生效保护。

## 10. GitHub 合并与并发安全

结合远端真实配置及历史，不仅阅读 YAML：

- 确定自动合并允许的分支、变更类型、风险级别、身份与资格判定；高风险包括认证授权、敏感数据、迁移、部署、依赖、Prompt / Agent 权限及门禁自身变更，按项目上下文调整。
- 核对风险分类的决定者与修改权限：AI 作者、PR 标签、路径过滤或自动化能否自行降低风险等级，跳过本应执行的专项测试、AI Evaluation 或人工审批。追踪分类输入 → 判定 → 必需门禁的强制执行证据及降级约束，记录于现有矩阵；自报风险或标签本身不是证明，无法核对实际强制执行时标为未验证。
- Rulesets / Branch Protection 是否在目标分支实际启用，Required Checks 名称与可信来源是否准确匹配；失败、缺失、跳过、取消、neutral 是否会被整体资格判断错误接受。
- 证据是否覆盖最新 PR HEAD 与最新目标分支的组合；严格更新分支或 merge queue 是否提供相应保证，目标分支移动后是否使旧结果失效。
- merge queue 使用时是否有对应 `merge_group` 验证，队列批次 / 合并组是否覆盖组合代码；没有队列时，现有串行化或重新验证能否解决竞态。
- 并行 PR、自动 rebase、过期审批、自动重试、机器人身份、直接 Push、管理员及 App bypass 是否形成绕过路径。
- CI / 安全配置、CODEOWNERS 及合并资格逻辑是否受可信独立审查保护；自动化能否同时改变保护规则和提交状态。

## 11. 依赖、密钥、Actions 与供应链

- 依赖来源、锁文件、完整性校验、更新策略及漏洞处理是否符合项目风险；第三方脚本、生成代码、制品来源是否可追踪。
- Actions / 可复用工作流是否固定可信版本，更新是否审查；Token 权限、Secrets、OIDC 受众与分支限制是否合理。
- `pull_request_target`、`workflow_run`、Fork PR、缓存 / Artifact 传递和自托管 Runner 是否混用不可信代码与高权限身份。
- 密钥扫描和响应是否实际覆盖提交、日志、制品与历史风险；只记录泄漏位置及脱敏标识，不复制秘密。
- SBOM、签名或来源证明按制品和威胁模型判断价值，不因缺某工具自动报错。

## 12. 构建、部署、配置、迁移与回滚

- 构建是否可复现，依赖 / 工具链是否固定；制品是否绑定代码 SHA、构建配置、来源与发布版本，验证制品是否就是部署制品。
- 环境配置与秘密是否分离，测试 / 预发布 / 生产差异是否影响验证；发布身份与环境保护是否生效。
- 数据库迁移是否考虑顺序、并发、锁、前后兼容、失败中断与恢复；应用回滚能否适配已变更的数据结构。
- 数据恢复、回滚 / 前滚及备份恢复是否有可用记录与明确责任；不可逆变更是否额外审批并验证恢复路径。

## 13. 可观测性和事故恢复

- 日志、指标、链路和告警能否关联请求、版本、制品、模型 / Prompt / 索引并定位失败；数据是否脱敏。
- 发布后验证、灰度、健康检查和异常阈值是否覆盖真实关键路径，失败后谁停止发布或执行恢复。
- 事故响应、Runbook、权限、备份和恢复演练是否与实际环境匹配；故障后能否定位引入变更及重现条件。

## 14. 持续改进反馈

- Bug、Bad Case、PR Review 和事故是否追踪根因、修复及验证，重复问题是否进入确定性回归测试、结构 / 静态规则、接口契约、规范或工具反馈。
- 回归用例是否确实捕获原失败，新增约束是否覆盖同类风险；例外、隔离测试和临时门禁是否按期复查。
- 不把每次失败都归因于 Prompt 不够长或缺 Skill；先判断哪个可执行反馈最有效、最便宜。

## 15. 效率和过度工程

- 重复安装、重复测试 / Eval、无效审批、冗余阶段、全量上下文和过大 PR 的成本是否有证据；比较耗时、Token、维护与故障收益。
- 确定性测试能否前置，风险低的改动能否复用相容证据、采用可靠的影响分析和缓存；完整回归仍覆盖关键风险。
- Flaky 重试是否掩盖缺陷，昂贵 Eval 是否真由相关变化触发；探索评测和正式门禁的执行频次是否合理。
- 简化建议给出最小变动、保留的保障、预计收益依据及验证方式；没有测量时只列候选，不编造节省比例。
