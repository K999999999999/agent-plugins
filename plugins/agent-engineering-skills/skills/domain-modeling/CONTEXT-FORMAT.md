# CONTEXT.md 格式

## 基本结构

```md
# {上下文名称}

{用一到两句话说明这个上下文是什么，以及为什么存在。}

## 语言

**{规范术语}**：
{用一到两句话定义这个术语。}
_避免_：{容易混淆的同义词或近义词}

**{另一个规范术语}**：
{用一到两句话定义这个术语。}
_避免_：{容易混淆的同义词或近义词}
```

## 编写规则

- **明确选择规范术语。** 同一个概念有多个叫法时，选择一个主术语，并把容易混淆的其他叫法列在 `_避免_` 下。
- **定义保持紧凑。** 通常一到两句话，说明它“是什么”，不要描述实现过程。
- **只记录领域特有概念。** 通用编程概念（例如超时、错误类型、工具函数）即使大量使用，也不属于领域上下文。
- **按自然领域分组。** 术语形成明显的概念簇时使用小标题；否则使用平铺列表。
- **不写实现细节。** 类名、函数名、数据库表、接口路径、框架和测试步骤应放在其他事实源，而不是 `CONTEXT.md`。
- **不写临时讨论。** 只有已经确认且会影响后续理解的领域语言才进入文件。

## 单上下文与多上下文仓库

### 单上下文

大多数仓库使用根目录的一个 `CONTEXT.md`。

### 多上下文

根目录的 `CONTEXT-MAP.md` 记录每个上下文的位置和它们之间的关系：

```md
# 上下文映射

## 上下文

- [Context A](./src/context-a/CONTEXT.md)：负责一组相关领域概念
- [Context B](./src/context-b/CONTEXT.md)：负责另一组相关领域概念
- [Context C](./src/context-c/CONTEXT.md)：负责第三组相关领域概念

## 关系

- **Context A → Context B**：Context A 发布一个已确认的领域事实，Context B 根据该事实继续处理
- **Context B → Context C**：Context B 发布另一个领域事实，Context C 消费它
- **Context A ↔ Context C**：两个上下文共享经过明确约定的稳定概念
```

处理多上下文仓库时：

- 如果存在 `CONTEXT-MAP.md`，先读取它并定位当前主题；
- 如果只有根目录 `CONTEXT.md`，按单上下文处理；
- 如果两者都不存在，等第一个术语确认后再创建根目录 `CONTEXT.md`；
- 当前主题对应哪个上下文不明确时，先提问。
