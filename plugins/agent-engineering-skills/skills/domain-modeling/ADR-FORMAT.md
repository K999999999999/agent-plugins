# ADR 格式

ADR（Architecture Decision Record，架构决策记录）存放在 `docs/adr/`，使用连续编号：

```text
0001-上下文边界.md
0002-持久化技术选择.md
```

只有确实需要记录第一条 ADR 时才创建 `docs/adr/` 目录。

## 最小模板

```md
# {简短的决策标题}

{用一到三句话说明背景、决定是什么，以及为什么这样决定。}
```

ADR 可以只有一个段落。价值在于记录“做了什么决定”和“为什么”，而不是堆积格式化章节。

## 可选章节

只有确实有长期价值时才添加：

- **Status（状态）**：`proposed`、`accepted`、`deprecated` 或 `superseded by ADR-NNNN`；适合会被重新审视的决定；
- **Considered Options（考虑过的方案）**：被拒绝的替代方案值得长期记住时使用；
- **Consequences（后果）**：需要提醒未来维护者的非显然后果时使用。

大多数 ADR 不需要这些章节。

## 编号规则

创建 ADR 前扫描 `docs/adr/`，找到当前最大编号，然后加一。不要覆盖已有 ADR，也不要因为文件名排序异常而重复编号。

## 何时创建 ADR

以下三个条件必须全部满足：

1. **难以逆转**：以后改变决定的代价明显；
2. **没有背景会令人意外**：未来维护者会问“为什么要这样做”；
3. **存在真实权衡**：有合理替代方案，并基于明确理由选择了当前方案。

如果决定容易撤销、没有意外性或没有真正的替代方案，就不要创建 ADR。

## 典型适用范围

- **架构形态**：例如采用 Modular Monolith（模块化单体），或将读模型投影到特定存储；
- **上下文之间的集成方式**：例如使用 Domain Event（领域事件），而不是同步 HTTP；
- **具有锁定成本的技术选择**：数据库、消息总线、认证提供方或部署目标；
- **边界和所有权**：例如某个上下文拥有一类领域数据，其他上下文只能通过稳定 ID 引用；
- **有意偏离常规做法**：例如因为明确约束而不使用 ORM；
- **代码中不可见的约束**：合规、外部服务合同或必须满足的时延要求；
- **非显然的替代方案取舍**：记录拒绝方案的理由，避免未来重复争论。

ADR 不用于记录普通实现步骤、临时调试过程、Ticket 清单或已经由项目规范明确规定的常规做法。
