# 领域建模

在设计过程中主动构建和校准项目的领域模型。这个 Skill 的职责不是单纯读取 `CONTEXT.md`，而是挑战模糊术语、设计边界场景，并在结论确定后把词汇和不可逆决策记录下来。

## 文件结构

大多数仓库只有一个领域上下文：

```text
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-领域决策.md
│       └── 0002-另一项决策.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，说明仓库有多个上下文。先读取映射文件，确认当前主题对应哪个上下文：

```text
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                    ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/           ← Context A 的决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/           ← Context B 的决策
```

文件按需创建：

- 没有 `CONTEXT.md` 时，等第一个术语确认后再创建；
- 没有 `docs/adr/` 时，等第一个 ADR 确实需要时再创建；
- 不为了“完整结构”预先创建空文件或空目录。

## 开始前

先读取与当前主题相关的事实源：

- `AGENTS.md` 或 `CLAUDE.md`；
- `CONTEXT-MAP.md`（如果存在）；
- 当前上下文的 `CONTEXT.md`；
- 相关 `docs/adr/`；
- 相关架构、Spec、测试和代码。

遵循项目规定的事实源优先级。不要因为旧代码、旧文档或生成物看起来不同，就自行改写已经确认的领域事实。

## 领域模型工作方式

### 挑战术语冲突

用户使用的词与现有 `CONTEXT.md` 定义冲突时，立即指出冲突并要求确认。例如：

> 当前 Glossary 将“实体”定义为独立且可识别的领域对象，但你描述的是“实体配置”。这里需要确认使用同一个术语，还是建立两个不同概念。

不要默默接受同一个词在不同地方代表不同概念。

### 收紧模糊或重载语言

当一个词过于宽泛、含义不明确或有多个候选概念时：

1. 指出歧义；
2. 提出少量候选的规范术语和定义；
3. 用具体场景验证它们的边界；
4. 等用户确认后，再将最终术语写入 `CONTEXT.md`。

不要为了显得完整而创造未经确认的领域对象、关系或规则。

### 用具体场景施压测试

讨论领域关系时，至少设计一个正常场景和一个边界场景。优先检查：

- 空结果、零值和缺失值；
- 权限、租户或数据范围边界；
- 多对象、多指标或多轮状态；
- 失败、超时、重试和重复请求；
- 用户表述与代码实际行为不一致的情况。

场景的目的不是扩大需求，而是确认概念边界和业务规则。发现超出当前范围的情况时，记录为 Out of Scope 或待确认问题。

### 对照代码和文档

当用户描述系统行为时，检查相关代码、测试和文档是否一致。如果发现冲突，明确区分：

- 当前实现事实；
- 已确认的领域规则；
- 用户希望实现的目标；
- 尚未确认的假设。

不要把实现现状直接当作业务真相，也不要把模型推测当作业务事实。

## 更新 CONTEXT.md

领域术语确认后立即更新对应的 `CONTEXT.md`，不要把已经确定的词汇留在临时对话中。格式遵循 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

`CONTEXT.md` 只记录领域词汇和业务含义：

- 记录项目中具有特定含义的规范术语；
- 为同义词或容易混淆的词标记 `_Avoid_`；
- 定义应简短，说明“它是什么”，通常不超过一两句话；
- 只保留项目领域特有的概念；
- 不写实现细节、类名、数据库表、接口路径、测试步骤、Spec 或临时讨论。

如果是多上下文仓库，更新正确的上下文文件，并在需要时同步维护 `CONTEXT-MAP.md` 的关系说明。上下文归属不清时先提问，不要自行选择。

## 谨慎创建 ADR

只有以下三个条件全部满足时，才建议创建 ADR：

1. 难以逆转：以后改变决定的代价明显；
2. 没有背景会令人意外：未来维护者会疑惑为什么这样做；
3. 存在真实权衡：确实比较过替代方案，并基于明确理由选择了当前方案。

如果缺少任意一个条件，就不要创建 ADR。普通实现选择、容易替换的库、一次性试验和显而易见的决定不需要 ADR。

ADR 必须在决定被确认后写入，并遵循 [ADR-FORMAT.md](./ADR-FORMAT.md)。重点记录“决定是什么”和“为什么”，不要把 ADR 写成详细实施方案或任务清单。

典型适用范围包括：

- 架构形态和上下文之间的集成方式；
- 带来明显锁定成本的基础设施或平台选择；
- 领域边界、数据所有权和明确的禁止项；
- 有意偏离常规做法的方案；
- 代码中不可见但会约束未来设计的外部条件；
- 值得长期记住的非显然替代方案取舍。

## 会话边界

本 Skill 可以：

- 澄清和记录领域术语；
- 更新 `CONTEXT.md`、`CONTEXT-MAP.md` 和必要的 ADR；
- 为后续 Spec、实现和测试提供稳定的领域语言。

本 Skill 不会自动：

- 编写业务代码；
- 把领域文档改写成 Feature Spec；
- 创建 Ticket、Issue 或 PR；
- 扩大当前需求范围；
- 提交代码或修改外部系统。

## 输出语言

默认使用中文。Skill 名称、命令名、API、类名、函数名、文件路径、代码和必要的原始术语保持原样。
